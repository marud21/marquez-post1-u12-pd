# ADR-001: Capas simples para la persistencia; el seam de notificación ya cubre el próximo cambio conocido

## Estado

Aceptado — 2026-11-16

## Contexto

Con Chain of Responsibility (RF1), Strategy (RF2) y Observer (RF3) integrados, hay que decidir si el
sistema migra a arquitectura Hexagonal completa (puertos e interfaces intermedias para todas las
dependencias externas) o se mantiene en capas simples. La guía (sección 6.2) recomienda Hexagonal "en
sistemas que sobrevivirán 3 años o más con cambios de infraestructura". Datos del proyecto:

- **Persistencia:** una sola base relacional (H2 en el laboratorio, una base relacional corporativa en
  producción), accedida por un único servicio con un único repositorio y una consulta derivada. No existe
  ningún plan, presupuesto ni requisito de cambiar de motor ni de tener una segunda fuente de datos. El
  criterio de la guía **no se cumple**: hay vida útil esperada, pero no cambios de infraestructura previstos.
- **Notificación:** Contabilidad anunció, para el próximo trimestre, una integración por API externa para
  programar el pago de las solicitudes aprobadas, y Finanzas mencionó un panel de métricas. Aquí sí hay un
  cambio de infraestructura **con fecha**, pero ya existe la abstracción `ObservadorCambioEstado`, definida
  en `procesamiento.notificacion` e invocada por el servicio sin conocer implementaciones concretas.

## Decisión

1. **Persistencia en capas simples.** `SolicitudReembolsoService` sigue dependiendo directamente de
   `RepositorioSolicitudesJpa` (Spring Data JPA), sin una interfaz de puerto `RepositorioSolicitudes` ni un
   adaptador. Un puerto hoy sería una abstracción especulativa (YAGNI) sin ningún caso de uso que la
   requiera. El modelo de dominio sí se mantiene libre de JPA mediante `META-INF/orm.xml`, porque eso no
   cuesta indirección en el código.
2. **Notificación sin cambios.** `ObservadorCambioEstado` ya es el *seam* necesario: la integración de
   Contabilidad consistirá en cambiar la implementación interna de `NotificadorContabilidad` (o agregar un
   observador `NotificadorPagosApi`) que llame a la API externa. No hay que modificar
   `SolicitudReembolsoService` ni los demás observadores. El panel de métricas será otro `@Component` que
   implemente la interfaz.

## Consecuencias

**Positivas**

- No se agregan interfaces, adaptadores ni mappers de persistencia sin un caso de uso real.
- El único cambio de infraestructura con fecha conocida (integración de Contabilidad) ya tiene su punto de
  extensión listo y verificado por la Regla 4 de `ReglasArquitectura`.
- Las reglas de ArchUnit protegen los límites que sí existen: `procesamiento` no depende de JPA, Spring Data
  ni de los adaptadores, y el controlador solo habla con la aplicación y el dominio.

**Negativas**

- Si en el futuro se necesita cambiar de motor de base de datos o agregar otra fuente, el puerto de
  persistencia deberá introducirse retroactivamente (el cambio se concentra en un servicio y un repositorio);
  se acepta esa deuda técnica de forma consciente.
- La llamada a la API de Contabilidad ocurrirá dentro de la transacción de `cambiarEstado`; si la API es
  lenta o falla, habrá que pasar a notificación asíncrona (por ejemplo, outbox o evento posterior al commit).
  Esa decisión se tomará cuando se conozca el contrato real de la API.
- Un revisor que espere simetría total (puertos en todas las dependencias externas) puede interpretar la
  asimetría como inconsistencia si no lee este ADR.

## Señales para revisar esta decisión

- Aparece un requisito de segunda fuente de datos o de migración de motor.
- La integración con Contabilidad exige reintentos, idempotencia o desacople temporal (procesamiento
  asíncrono).
